# V0.1 Generic TextMap Hash References

日期：2026-10-06。扩展版本：0.1.0。仅扩大 numeric `Hash` → TextMapCHS；不实现 ID references。

## 来源规则、格式调查与实现

V0 每次 Hover/Definition 都 `getText()` 整份来源并 `parseTree()` 建立 DOM。
对 605,087 行的 AvatarSkillConfig 和 1,149,998 行的 StageConfig，这会把所有无关内容
的读取、AST 分配与数值转换带入一次局部引用操作，因此不适合直接扩大适用范围。

V0.1 使用现有 `jsonc-parser` scanner，仅读取 `document.lineAt(position.line)`。
识别解码后精确为 `Hash` 的 string key、冒号及 JSON numeric token，检查光标落在
数字半开区间内、scanner error、前置 key 边界和后置数字边界。最多保留三个前置
token；来源 Range 直接使用同一行的 UTF-16 字符位置，不计算全文件 offset。
hash 使用 `lineText.slice(start, start + length)`，不读取 numeric scanner value，
不调用 Number/parseInt/JSON.parse 建立身份。合法负数、小数、指数词法也原样保留。

只读调查使用 `rg --json --glob '*.json' '"Hash"[ \t]*:' ../TurnBasedGameData` 的
匹配行，再逐行用 scanner 区分 key/冒号/value；没有来源 JSON DOM、schema mining、
索引或 dataset 写入。将全部候选交给新 helper 的复核结果：

| 观察 | 结果 |
| --- | ---: |
| 匹配 JSON 文件 | 10,179 |
| 匹配行 / numeric Hash 候选 | 779,227 |
| 新 helper 正确保留 raw lexeme | 779,227 |
| 观察到的跨行 value / 非数字 value | 0 / 0 |
| 未识别候选 | 0 |
| 匹配行最大长度 | 83 个 UTF-16 字符 |

这是当前快照中 rg 可见、raw key 为 `"Hash"` 的格式调查，不是完整文件合法性审计。
因此本轮选择 current-line recognition；不引入 nearby-window/full-document fallback。
当前行字符串、line/block comment、相似字段名及非法 numeric boundary 均不会误触发。
跨行属性、跨行注释上下文和任意非标准 JSON 不属于保证范围；不声称检查完整 document。
极长的单行仍会增加局部成本，不能把 current-line 方案宣称为对任意 minified JSON 恒定耗时。

Provider 现在匹配 workspace 内本地 `**/*.json`，不要求父字段、文件名、root schema
或数字大小。保持 `onLanguage:json`，增加精确 `workspaceContains:TextMap/TextMapCHS.json`
激活事件，因此 JSON 语言服务关闭或 Plain Text 模式也能工作。目标始终来自来源
所属 workspace folder，不猜 dataset root、不跨 root 解析。

命中时沿用不受信任的 `MarkdownString.appendText` Hover 和真实 `vscode.Location`。
key/target 缺失时均无 Hover/Definition；取消、变化、不适用保持安静，实际失败或
unsupported target layout 写 Output Channel。没有新增 UI、command 或 reference framework。

## 大来源与 target 性能

以下是本机单次观察，不是 SLA、cold disk benchmark 或跨平台保证。local recognition
列为 1,000 次当前行 helper 调用的 median；每个实际案例扫描的行均只有 **33** 个字符。
VS Code 自身打开/镜像 document 的成本另列，未作为 RefAtlas 来源解析预热。

| 来源 / 案例 | bytes / 行数 | local median | 打开 document | 首次 Hover 链（Plain Text） | 缓存 Hover 链 |
| --- | --- | ---: | ---: | ---: | ---: |
| AvatarConfig / AvatarName | 240,466 / 7,529 | 0.0010 ms | 50.83 ms | 160.43 ms | 20.85 ms |
| AvatarSkillConfig / SkillName | 11,438,925 / 605,087 | 0.0008 ms | 182.62 ms | 182.99 ms | 3.01 ms |
| AvatarSkillConfig / SkillDesc | 同上，已打开 | 0.0006 ms | 0.03 ms | 38.14 ms | 1.25 ms |
| StageConfig / StageName | 26,939,432 / 1,149,998 | 0.0006 ms | 468.04 ms | 272.28 ms | 32.67 ms |

这些 Hover 链通过 `vscode.executeHoverProvider` 调用，包含 VS Code command/IPC 调度
及 target 查找，不是孤立的 RefAtlas 函数耗时。测量时 TextMap 未在编辑器中打开，
使用原有 disk-stream resolver；Definition verification 用独立只读流，不打开目标 editor。
随后切回 JSON mode 的一次 cached command chain 分别约 **208.25、308.34、326.13、
503.97 ms**，还包含其他 JSON providers/语言模式初始化；不将它们误报为 target cache 时间。

5 ms heartbeat 在 SkillName 和 StageName 的首次/缓存 Hover 链中最大实际间隔分别为
**48.90 / 65.46 ms**；前一次 Stage 运行还观察到 **99.64 ms**，首次链约 **460.42 ms**。
因此不能宣称整个 Extension Host/UI 完全无阻塞。来源 helper 没有随全文件大小扩大
工作量，但 editor/document 生命周期、其他 providers 和 GC 等成本仍会影响执行链；
本次未完成对这些成本的归因或视觉流畅度审计。

RSS 也是整个 host 的瞬时观察：Stage Hover 窗口增量约 **2.66 MiB**，包含 JSON-mode
检查等的完整 case 增量约 **66.26 MiB**；部分 case 出现 GC 后的负增量。
这些不是峰值或 resolver 独立内存承诺。没有新增来源 DOM、worker 或内存索引。

Target 层的独立 Node 测量使用每项新建 resolver，保留原有 **64-entry successful-only**
版本缓存。中/末部 key 直接从 TextMap 指定位置选择，没有虚构对应 source field。

## 查找架构与下一步判断

`src/textmap.ts` 未修改：仍是异步 UTF-8 流、exact decoded-key lookup、提前停止、
每 256 行让出 event loop、版本化成功缓存，以及 editor 内未保存目标路径。
FEFF/string fidelity 回归保留；没有复制旧 decoder 或宣称全 TextMap 审计。

目前没有功能正确性 blocker 要求索引或更复杂基础设施。**末部和 missing 的约 0.4 秒
线性扫描是可感知的首次查找成本，不能忽略。** core heartbeat 没有出现明显持续阻塞，
取消很快，但 missing 因未缓存会再次扫描。是否接受这类 Hover 体验应由 review 决定。
若需要后续优化，最小讨论候选是版本化的小型 negative cache（重复 missing）或
TextMap-specific lazy/progressive in-memory lookup（首次 late）；本轮没有实现任何候选。
它们也不能直接解释/解决 JSON-mode command chain 的额外成本。
